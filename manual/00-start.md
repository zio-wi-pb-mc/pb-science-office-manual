# Pierwsze zajęcia — start projektu

Celem pierwszych zajęć nie jest rozpoczęcie programowania.

Najpierw organizujemy zespół, poznajemy problem i tworzymy pierwsze rzeczywiste zadania projektowe.

## 1. Dostęp do projektu

Każdy student powinien:

1. posiadać konto GitHub,
2. zaakceptować zaproszenie do organizacji `zio-wi-pb-mc`,
3. uzyskać dostęp do repozytorium `pb-science-office`,
4. zapoznać się z niniejszym manualem.

## 2. Profil studenta

Każdy student tworzy jedno Issue:

**Issues → New issue → Student profile**

Tytuł:

`[PROFILE] Imię Nazwisko`

Profil służy do utworzenia możliwie zrównoważonych podów.

## 3. Podział na pody

W jednej grupie PS powstaną trzy pody po około 4 osoby.

Każdy pod otrzyma tymczasowego leada na fazę Discovery.

Lead nie jest przełożonym pozostałych osób. Odpowiada przede wszystkim za:

- zebranie statusu prac,
- pilnowanie aktualności Issues,
- wykrywanie blockerów,
- kontakt z prowadzącym,
- pilnowanie, aby każdy miał własne zadanie.

Po fazie Discovery lead może zostać zmieniony.

## 4. Pierwsze rzeczywiste zadanie

Każdy student podczas pierwszych zajęć tworzy co najmniej jedno rzeczywiste Issue typu:

**Task / Feature**

Nie tworzymy sztucznych zadań treningowych. Zadania wykonane podczas pierwszych zajęć staną się częścią analizy projektu.

Każde zadanie powinno:

- mieć jednego właściciela,
- być możliwe do wykonania w około tydzień,
- mieć jasno określony rezultat,
- zawierać mierzalne kryteria akceptacji,
- wskazywać źródła informacji lub pytania wymagające wyjaśnienia.

## 5. Discovery 1 — zakres pracy podów

### POD A — istniejący system i zgodność funkcjonalna

Przykładowe zadania:

1. Inwentaryzacja funkcjonalności istniejącego systemu.
2. Aktorzy, role i uprawnienia w obecnym systemie.
3. Reguły finansowe: budżet, wydatki, rezerwacje i saldo.
4. Wstępna klasyfikacja funkcji legacy jako P0 / P1 / P2.

### POD B — procesy i formularze

Przykładowe zadania:

1. Katalog formularzy i procesów Działu Nauki.
2. Analiza procesu wniosku / kosztorysu pracy.
3. Analiza delegacji i konferencji krajowych/zagranicznych.
4. Wspólne elementy formularzy, załączników i dokumentów PDF/DOCX.

### POD C — platforma, integracja i jakość

Przykładowe zadania:

1. Plan środowiska Django + PostgreSQL + Docker.
2. Identyfikacja wspólnych usług: auth, workflow, documents, audit, attachments.
3. Strategia testów, CI i kontroli jakości.
4. Migracja ze starego systemu: ryzyka, dane i pytania do administratora.

Jeżeli pod ma więcej lub mniej niż cztery osoby, zakres można odpowiednio podzielić lub połączyć.

## 6. Review

Każdy student powinien przeczytać co najmniej jedno Issue utworzone przez inną osobę ze swojego poda.

Jeżeli zadanie jest niejasne, należy dodać komentarz z konkretną uwagą lub pytaniem.

## 7. Rezultat pierwszych zajęć

Na koniec zajęć powinny istnieć:

- profile wszystkich studentów,
- trzy pody,
- trzech tymczasowych leadów,
- minimum jedno rzeczywiste Issue na każdego studenta,
- pierwszy zestaw zadań Discovery,
- lista najważniejszych pytań i blockerów.

Lead każdego poda przedstawia prowadzącemu krótki status oraz numery utworzonych Issues.
